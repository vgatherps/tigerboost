# Rosetta 2 and AVX2: what is publicly known (sonnet web research, 2026-09-28)

Rosetta 2 on macOS 15+ does execute AVX and AVX2 (added with Sequoia, publicized as part of Game Porting Toolkit 2), but not AVX-512, and BMI1/BMI2/F16C were added later in macOS 15.4; separately, Rosetta's self-reported CPUID/sysctl capability flags stay off by default and only flip on with the ROSETTA_ADVERTISE_AVX=1 environment variable, which is exactly the split the probe on this machine is seeing. Every independent measurement I found shows AVX2 code running slower under Rosetta than the SSE2 build of the same algorithm — the opposite of real x86-64 hardware — so Rosetta wall-clock timing has no predictive relationship to a real x86 CPU and is useful only for "does it crash," not for performance comparison. No source, Apple's or third-party, makes any correctness guarantee beyond "doesn't crash"; one hedged report of wrong AVX2 output exists, and no public source documents flag semantics, NaN payload handling, or denormal/rounding fidelity for the AVX2 path specifically, so correctness checking under Rosetta should be treated as spot-checking, not an oracle.

## 1. Which extensions are supported

AVX and AVX2 execute under Rosetta as of macOS 15 Sequoia, rolled out with Game Porting Toolkit 2 and announced at WWDC 2024 (https://appleinsider.com/articles/25/01/16/game-porting-toolkit-2-exits-beta-to-help-developers-move-to-macos, https://9to5mac.com/2024/07/03/apple-game-porting-macos-games-ios/). AVX-512 is explicitly not supported and traps with "illegal hardware instruction" — this is the same line from Apple's own Rosetta documentation page that predates Sequoia (quoted by multiple secondary sources, e.g. https://medium.com/macoclock/m1-rosetta-2-limitation-illegal-hardware-instruction-a3b48fae02e); I could not fetch the live body text of Apple's page itself (https://developer.apple.com/documentation/apple-silicon/about-the-rosetta-translation-environment — my fetch tool got only the title, the page is JS-rendered), so I can't confirm whether Apple has since edited that sentence to carve out AVX/AVX2. FMA is reported working; BMI1/BMI2 and F16C were missing at Sequoia's initial AVX2 rollout and were added in macOS 15.4 per a user-reported update on an Apple developer forum thread, though Rosetta running inside a Linux VM still lacks AVX advertising entirely (https://developer.apple.com/forums/thread/769486). A concrete example of the BMI1 gap: Stockfish's AVX2 binary crashed under Rosetta on macOS 15 not because of the AVX2 vector ops but because it also emits the BMI1 opcode `blsrq` (https://github.com/official-stockfish/Stockfish/issues/5707) — relevant since a plain `-mavx2` build without `-mbmi` (like the probe on this machine) avoids that trap.

A widely circulated claim that AVX2-under-Rosetta is exclusive to M4/ARMv9 hardware (sourced to YouTuber Vadim Yuryev via https://wccftech.com/apple-game-porting-toolkit-2-supports-avx2-instruction-set/) looks wrong: hands-on AVX2-under-Rosetta testing (https://github.com/carsongoodwin32/rosetta2_avx_dive) and a report of AVX2 in Sequoia beta 1 (https://x.com/never_released/status/1800408706317943237) both date to June 2024, months before the M4 shipped, and a MacRumors forum commenter separately noted M4 doesn't even implement SVE2 — it's still plain NEON (thread found via search, not independently re-fetched). I'm flagging this as third-party and contradicted rather than confirming or denying it as fact.

On the sysctl/CPUID discrepancy: `hw.optional.avx2_0` reads 0 under Rosetta by default even though AVX2 instructions execute correctly when issued unconditionally — this is exactly what the probe on this machine observed. The mechanism is an opt-in environment variable, `ROSETTA_ADVERTISE_AVX` (default 0/off): setting it to 1 makes Rosetta's synthesized CPUID/feature responses report AVX/AVX2 to translated code (https://github.com/Heroic-Games-Launcher/HeroicGamesLauncher/issues/4193, https://developer.apple.com/forums/thread/769486). So execution support and capability advertisement are two independent switches — the former has been unconditionally on for AVX/AVX2 since Sequoia, the latter is opt-in and off by default, which is why a `clang -mavx2` binary runs correctly while `sysctl` still says no.

## 2. How the translation works

General-purpose Rosetta 2 mechanics (pre-AVX2, describing the SSE2 path) come from Dougall Johnson's reverse-engineering write-up: ahead-of-time whole-binary translation with JIT fallback, ~1.64x code-size expansion measured on sqlite3, x86 flag semantics reproduced via ARM's FEAT_FlagM/FlagM2 (CFINV, RMIF, SETF8/16) plus an undocumented M1-specific extension for the adjust/parity flags, x86-matching NaN/tininess semantics via ARM's FEAT_AFP alternate floating-point mode, and full 80-bit x87 soft-float emulation (https://dougallj.wordpress.com/2022/11/09/why-is-rosetta-2-fast/). This piece is from November 2022 and explicitly doesn't cover AVX/AVX2, which didn't exist under Rosetta yet.

For AVX2 specifically, the only public disassembly-level look I found is the carsongoodwin32 repo, done against the Sequoia beta before AVX2 shipped in a public release: it shows 256-bit ops like `vpxor`, `vmovdqu`, `vpaddd` compiling down to NEON instructions on 128-bit registers, consistent with splitting a 256-bit YMM operation into a pair of 128-bit NEON lane ops (https://github.com/carsongoodwin32/rosetta2_avx_dive). That repo does not give instruction-by-instruction detail beyond this.

I found no public source — no reverse-engineering write-up, Apple document, or forum thread — documenting Rosetta's translation of `vcmppd` with the extended AVX predicates, `vmovmskpd`, `vinsertf128`, `vmovhpd`/`vmovsd` lane loads, `vaddsd` with a memory operand, `vgatherqpd`, `vpshufb`, `vpermq`, or MXCSR/DAZ handling specifically. The `vzeroupper`-related hits my searches turned up were all pre-Sequoia issues from unrelated projects (Homebrew's "AVX crashes in Rosetta" report from 2020/2021, https://github.com/Homebrew/homebrew-core/issues/67713) and reflect the era before AVX existed under Rosetta at all, not current behavior. For gather instructions specifically: NEON has no direct gather-load equivalent, so if `vgatherqpd` runs at all under Rosetta it must be doing something more expensive than a single vector load — this is my inference from the ISA gap, not something any source states or measures.

## 3. Performance measurements and predictive value

A hands-on Japanese blog benchmark (SFMT19937 SIMD RNG, 100M generations) measured: native ARM64 NEON 49-51ms; x86-64/SSE2 under Rosetta 52-77ms (close to native); x86-64/AVX2 under Rosetta 183-207ms — roughly 3x slower than the same code's SSE2 path and ~4x slower than native ARM64; AVX-512 crashed outright (https://qiita.com/STDNUL/items/a17bbba6202835407e6b). The carsongoodwin32 repo's initial numbers similarly showed AVX2 running ~13-30% slower than SSE2 under Rosetta, though the author also reported an integer-sum mismatch between build variants and later opened a follow-up issue titled "X86 Codegen differences between Clang and GCC" — suggesting at least part of that discrepancy traced to compiler codegen/reduction-order differences rather than a Rosetta translation bug, though I couldn't read the closed issue's body to confirm the connection is exactly that (https://github.com/carsongoodwin32/rosetta2_avx_dive). Separately, in the Stockfish thread, even Stockfish's plain x86_64/popcnt build ran slower under Rosetta than Stockfish's native ARM64 build (https://github.com/official-stockfish/Stockfish/issues/5707).

Every measurement found agrees on one thing: AVX2 is slower than SSE2 under Rosetta, which is backwards from real x86-64 hardware, where AVX2 normally beats SSE2 for the same work. That inversion by itself means Rosetta wall-clock timing reflects Rosetta's own translation and NEON lane-splitting cost, not the x86 ISA's cost model — no source claims otherwise or shows a case where Rosetta AVX2 timing tracked real x86 timing. Its only defensible use is confirming code runs without trapping and checking numeric output; it has no established value for relative or absolute performance estimation of the same kernel on real x86-64 hardware.

## 4. Correctness caveats

I found no public source addressing `ucomisd` flag fidelity (CF/ZF/PF), signaling-vs-quiet NaN payload preservation, or denormal/rounding-mode behavior for AVX2 under Rosetta specifically. The only floating-point-fidelity claim available is Dougall Johnson's description of FEAT_AFP matching x86 NaN/tininess semantics for the pre-AVX2 SSE2/x87 path (https://dougallj.wordpress.com/2022/11/09/why-is-rosetta-2-fast/) — not confirmed to extend to AVX2. One Stockfish issue commenter reported Rosetta's AVX2 translation producing different results run-to-run versus a reference, but immediately caveated that their own test code might contain undefined behavior, so it's a lead rather than a confirmed bug (https://github.com/official-stockfish/Stockfish/issues/5707). The one solidly-sourced trap is BMI1 opcodes (e.g. `blsrq`) incidentally emitted by `-mavx2 -mbmi` builds causing "illegal hardware instruction" prior to macOS 15.4, and reportedly still failing under Rosetta-in-a-Linux-VM after 15.4 (https://developer.apple.com/forums/thread/769486). I found no macOS 15.x point-release notes documenting AVX2-translation-specific bug fixes; my attempt to fetch Apple's own 15.4 release notes page returned no usable body text, and the BMI1/F16C-added-in-15.4 claim is a user report on the developer forum, not an Apple release note I could independently verify.

## 5. Practical mechanics

`arch -x86_64` on a fat or x86_64-only binary is the standard, sufficient way to invoke Rosetta translation across every source I found — no other flag is described as necessary. On signing: Apple's own security documentation states translated x86_64 code is permitted to execute through Rosetta with no signature information at all, i.e. unsigned x86_64 binaries still run (https://support.apple.com/guide/security/rosetta-2-on-a-mac-with-apple-silicon-secebb113be1/web). A secondary write-up adds that when a binary is signed, its AOT-translated cache artifact is bound to that binary's code-directory hash and invalidated if the binary changes afterward — that's a cache-validity/security detail, not a requirement for AVX2 support (https://danielcosenza.com/posts/mac-rosetta2-translation/). I found no source stating AVX2 execution requires a specific deployment target or minimum-macOS `LC_BUILD_VERSION` embedded in the x86_64 binary; everything found treats AVX2 support as a property of the macOS version doing the translating (15.0+), not of what the binary itself declares — consistent with this machine's own working probe, though I could not find a source explicitly ruling deployment-target gating out either, so treat that as inference, not a documented fact. The only environment-variable control found is `ROSETTA_ADVERTISE_AVX=1` (also settable session-wide via `launchctl setenv ROSETTA_ADVERTISE_AVX 1`), which only changes what Rosetta's synthesized CPUID/sysctl responses advertise, not execution support itself; it's documented not to propagate into Rosetta running inside a Linux VM (https://developer.apple.com/forums/thread/769486). No `sysctl` write was found that flips instruction-level support — `hw.optional.avx2_0` is a read-only capability-advertisement flag, and the environment variable above is the only lever anyone reports for controlling it.
